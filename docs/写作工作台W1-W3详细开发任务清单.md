### 任务 1.1：写作入口与懒加载

- **目标**：在主界面侧边栏添加"写作"入口按钮，点击后以懒加载方式载入写作工作台模块，不阻塞主画布渲染。

  - 输入：用户点击 Sidebar 中的"写作"图标
  - 输出：`WritingStudio` 组件异步加载并渲染在主内容区，替代或叠加当前画布视图
- **状态结构建议**：


## W2：剧本解析器

### 任务 2.1：解析器核心引擎

- **目标**：实现纯前端纯文本→结构化 `ScriptBlock[]` 的解析函数，支持中文标准剧本格式，输出类型安全的 AST。
- **涉及组件**：
  - 新建 `scriptParser.ts` — 核心解析逻辑（纯函数，无 UI 依赖）
  - 依赖 `writingTypes.ts` 中的 `ScriptBlock` 类型定义
- **输入输出**：
  - 输入：`rawText: string`（单场或多场的剧本文本）
  - 输出：`ScriptBlock[]`，每个 Block 包含类型、行号、内容、元数据
- **状态结构建议**：

```ts
// writingTypes.ts 中新增
type ScriptBlockType =
  | 'scene_heading'
  | 'action'
  | 'character'
  | 'dialogue'
  | 'transition'
  | 'parenthetical';

interface ScriptBlock {
  id: string;              // 唯一标识，建议 `block-{lineNumber}-{index}`
  type: ScriptBlockType;
  lineNumber: number;      // 在原文本中的起始行号（1-based）
  endLineNumber: number;   // 在原文本中的结束行号
  text: string;            // 原始文本内容
  normalizedText: string;  // 去除修饰后的标准文本
  metadata?: {
    sceneNumber?: string;       // 场景编号，如 "一"、"1"
    location?: string;          // 地点，如 "咖啡厅"
    timeOfDay?: string;         // 时间，如 "日"、"夜"
    characterName?: string;     // 角色名，仅 character block 有
    transitionType?: string;   // 转场类型，如 "CUT TO:"、"渐黑"
    parentheticalText?: string; // 括号内表演提示，如 "(愤怒地)"
  };
}

interface ParseResult {
  blocks: ScriptBlock[];
  stats: {
    sceneCount: number;
    characterCount: number;
    dialogueCount: number;
    actionCount: number;
  };
  errors: ParseError[];
}

interface ParseError {
  lineNumber: number;
  message: string;
  severity: 'warning' | 'error';
}
```

- **验收标准**：
  1. **场景识别**：以下模式均被正确识别为 `scene_heading`：
     - `场景一：咖啡厅·日内`
     - `第一场 咖啡厅 - 日`
     - `1. INT. 咖啡厅 - DAY`
     - `场1：咖啡厅（日）`
     - `【场景一】咖啡厅 日内`
  2. **角色与对白识别**：独立一行的角色名（后紧跟一行对白）被解析为 `character` + `dialogue`：
     - `林初夏`（单独一行）→ `character`
     - `你说得对。`（紧跟其后）→ `dialogue`
     - 角色名后带括号提示：`林初夏（苦笑）` → `character`，括号内容存入 `parentheticalText`
  3. **动作描述**：不被上述规则匹配的普通段落归类为 `action`
  4. **转场识别**：`CUT TO:`、`渐黑`、`FADE IN` 等独立行识别为 `transition`
  5. **容错处理**：空行跳过，纯空格行跳过，无法识别的行标记为 `action` 并记录 warning
  6. **Block 的 `id` 稳定**：相同输入文本多次解析出的 Block ID 一致
- **风险点**：
  - 中文剧本格式极度不统一，正则覆盖度可能不足，需采用多策略匹配（正则 + 启发式）
  - 角色名与对白的"紧跟"关系：若角色名与对白之间有括号提示行（`parenthetical`），需正确关联
  - 场景标题中的时间词（日/夜/晨/昏/日内/夜外）提取可能有歧义，如"日本料理店"不应提取"日"为时间
  - `normalizedText` 的定义需与 W3 高亮渲染对齐：去除哪个层级的修饰符
- **后续给 W4-W7 预留**：
  - 解析器需输出行号映射（`lineNumber` → `ScriptBlock`），W4 Diff 需要按行对比
  - `ParseResult.stats` 预留扩展字段（W5 分镜生成时需要角色统计）
  - 解析器需支持增量解析（仅解析变更段落），W3 防抖 + W4 自动保存时避免全量重解析

### 任务 2.2：单元测试覆盖

- **目标**：为核心解析器编写 ≥ 8 种不同剧本格式的测试用例，解析准确率 ≥ 95%，覆盖率 ≥ 90%。
- **涉及组件**：
  - 新建 `scriptParser.test.ts` — 测试文件（Vitest）
  - 新建 `testFixtures/` — 测试用剧本样例目录
- **输入输出**：
  - 输入：8+ 份不同风格的剧本文本样例
  - 输出：测试报告（`npx vitest run` 通过）
- **状态结构建议**：无（纯测试代码）
- **验收标准**：
  1. 至少覆盖以下格式：
     - 中文标准格式（场景一：XXX·日内）
     - 好莱坞格式（INT. XXX - DAY）
     - 网文/轻小说格式（第X章 XXX）
     - 纯角色对白格式（无场景标题，仅角色+对白交替）
     - 混合格式（场景标题中文 + 对白英文角色名）
     - 带括号提示格式
     - 含转场标记格式
     - 极端格式（大量空行、无空格紧凑格式）
  2. 每条用例包含：输入文本、期望的 `ScriptBlock[]` 结构、期望的 `stats` 统计
  3. 解析准确率（Block 类型判断正确率）≥ 95%
  4. `errors` 数组在格式异常时正确报告 warning
  5. 测试文件通过 `describe` / `it` 组织清晰，每个用例有明确的中文描述
- **风险点**：
  - 测试样例编写工作量较大，建议先写 5 条核心用例确保通过，再逐步补充边界用例
  - 好莱坞格式与中文格式混用时，角色名可能既是英文又是中文，需明确优先级
  - parse 结果中 `sceneNumber` 的提取逻辑较复杂（"一" vs "1"），需专门测试
- **后续给 W4-W7 预留**：

## W3：编辑器高亮和右侧大纲

### 任务 3.1：编辑器高亮渲染

- **目标**：在编辑器区域用 textarea + overlay 方案实现语法高亮，场景标题、角色名、对白、动作分别以不同颜色/样式显示。
- **涉及组件**：
  - 新建 `HighlightEditor` — 编辑器组件（textarea + 透明 overlay）
  - 复用 W2 的 `scriptParser.ts`
  - 新建 `highlightTokens.ts` — Token 生成与主题映射
- **输入输出**：
  - 输入：用户键入或粘贴的剧本文本
  - 输出：带语法高亮的可视化文本
- **状态结构建议**：

```ts
// highlightTokens.ts
interface HighlightToken {
  startIndex: number;     // 在整个文本中的字符起始位置
  endIndex: number;       // 字符结束位置
  type: ScriptBlockType;
  className: string;      // Tailwind CSS 类名
}

interface HighlightTheme {
  scene_heading: string;   // 如 'text-blue-400 font-bold text-lg'
  action: string;          // 如 'text-gray-300'
  character: string;       // 如 'text-yellow-400 font-semibold'
  dialogue: string;        // 如 'text-white'
  transition: string;      // 如 'text-gray-500 italic'
  parenthetical: string;   // 如 'text-gray-400 italic'
}

// useWritingStore 中新增
editorContent: string;
editorTokens: HighlightToken[];
setEditorContent: (content: string) => void;
```

- **验收标准**：
  1. 采用 textarea + overlay 方案：textarea 透明（文字颜色设为 `transparent`），底层 overlay 渲染带颜色的相同文本（等宽字体 + 等尺寸）
  2. 场景标题以醒目颜色显示（如蓝色加粗），角色名以高亮色显示（如黄色），对白白色，动作灰色
  3. textarea 滚动与 overlay 滚动完全同步（同步 `scrollTop` 和 `scrollLeft`）
  4. 支持粘贴 5 万字剧本，高亮渲染延迟不超过 100ms（在防抖窗口内完成）
  5. 光标位置、选区在同步高亮层中正常显示（用户无感知）
  6. 主题色使用项目已有的 CSS 变量，支持明暗主题自动切换
- **风险点**：
  - textarea + overlay 双层层叠方案在字号、行高、换行上必须完全一致，稍有偏差即错位，这是最大技术风险
  - 中文等宽字体选择有限（`Microsoft YaHei` 等），若字号不一致则汉字与英文对齐困难
  - `contenteditable` 替代方案更灵活但复杂度更高，需评估是否改用 CodeMirror 6（轻量版）
  - 大文本粘贴瞬间可能卡顿，需配合 W3.2 的防抖机制
- **后续给 W4-W7 预留**：
  - 编辑器组件需支持 `readOnly` 模式（W4 分屏对比时，左侧版本为只读）
  - 需预留行号 gutter 区域（W4 Diff 需要在行号旁显示 +/- 标记）
  - 编辑器需暴露 `scrollToLine(lineNumber)` 方法，供 W3.4 大纲点击跳转
  - 编辑器需预留 `getSelectionRange()` 方法，W4 版本对比需要知道用户选中了哪几行

### 任务 3.2：防抖解析与性能优化

- **目标**：用户输入时解析器具备 300-500ms 防抖机制，避免每次按键都全量解析导致卡顿；大文本场景下采用全量解析 + 防抖策略。
- **涉及组件**：
  - 修改 `HighlightEditor` — 集成防抖
  - 新建 `useDebouncedParse.ts` — 防抖解析 Hook
  - 依赖 W2 的 `scriptParser.ts`
- **输入输出**：
  - 输入：用户实时键入的文本变化事件
  - 输出：防抖后的 `HighlightToken[]`，用于高亮层渲染
- **状态结构建议**：

```ts
// useDebouncedParse.ts
function useDebouncedParse(content: string, delay: number = 350): {
  blocks: ScriptBlock[];
  tokens: HighlightToken[];
  isParsing: boolean;
  stats: ParseResult['stats'];
}
```

- **验收标准**：
  1. 连续快速键入时（如按住一个键），解析器不在每次 `onChange` 时调用，仅在停止输入 350ms 后执行一次
  2. 粘贴大文本（5 万字）时，解析器最多执行一次（粘贴动作触发即时解析 + 后续输入被防抖拦截）
  3. `isParsing` 在解析期间为 `true`，可用于显示微型 loading 指示器
  4. 防抖 delay 可通过 props 配置，默认 350ms
  5. 防抖窗口内编辑器的 UI 响应不受影响（textarea 值即时更新，仅高亮延迟）
- **风险点**：
  - 350ms 防抖可能导致用户感知到"高亮闪烁"（输入后短暂无高亮，350ms 后突然上色），需在 UX 上评估是否接受
  - 增量解析实现复杂，建议 W3 先用全量解析 + 防抖，后续优化再考虑增量
  - React 18+ 的 `useDeferredValue` 可作为简易替代方案，但粒度较粗
- **后续给 W4-W7 预留**：
  - `useDebouncedParse` 需返回 `blocks` 而非仅 `tokens`，W4 版本保存需要完整的 `ScriptBlock[]` 做结构化存储
  - 防抖 Hook 需支持 `immediate` 模式（失焦时立即解析），W4 自动保存触发时使用

- **目标**：将 W3.1-W3.4 串联，确保编辑器输入→防抖解析→高亮渲染→大纲/人物更新→点击跳转的完整链路畅通。
- **涉及组件**：

  - `HighlightEditor` + `RightInfoPanel` — 数据流联通
